## 1. 문서 개요

**목적**: `1-domain-definition.md`(v0.4.0)에 정의된 도메인 모델·비즈니스 규칙을 기반으로, 제품 관점의 요구사항(범위, 우선순위, 일정, 기술 스택, 성공 지표)을 정의한다.

**도메인 정의서와의 관계**: 본 문서는 도메인 정의서를 대체하지 않는다. 용어·엔티티·비즈니스 규칙(BR-ID)·유스케이스(UC-ID)·수용 기준·Out of Scope·미결 이슈(OI-ID)는 도메인 정의서를 단일 출처(source of truth)로 참조하며, 본 문서에서 중복 정의하지 않는다.

---

## 2. 제품 개요

**문제**: 인증된 사용자별로 할일을 개인화하여 관리하고, 시작일/종료일 기반으로 진행 상태(시작 전/진행중/완료/지연)를 자동 파악할 수 있는 도구가 부재하다.

**목표**: 회원가입/로그인 기반의 개인용 웹 TodoList를 제공하여, 사용자가 할일을 카테고리별로 등록·조회·필터링·관리하고 일정 지연 여부를 즉시 확인할 수 있게 한다.

**타겟 사용자**: 학생 및 20대~50대 직장인. 별도의 상세 페르소나는 정의하지 않으며, "개인 일정을 웹에서 간단히 관리하려는 사용자" 수준으로 정의한다.

## 4. 범위

**In Scope**: 도메인 정의서 7장 UC-01~UC-09 전체(회원가입, 로그인, 회원정보 수정, 할일 등록/조회/필터링/수정/삭제, 카테고리 관리). 상세 설명·액터·수용 기준은 도메인 정의서 7장, 7.1절 참조.

**Out of Scope**: 도메인 정의서 8장과 동일 (공유/협업, 알림, 첨부파일, 우선순위·태그·반복 일정, 소셜 로그인, 다국어). 본 PRD에서 추가하는 범위 제외 항목은 없다.

UC-ID별 상세 설명과 수용 기준은 도메인 정의서 7장/7.1절을 참조한다. 아래는 2일 일정 기준 우선순위 구분이다.

| ----- | -------------- | -------- | ------------------- |
| UC-01 | 회원가입       | P0       | 포함                 |
| UC-02 | 로그인         | P0       | 포함                 |
| UC-04 | 할일 등록      | P0       | 포함                 |
| UC-05 | 할일 목록 조회 | P0       | 포함                 |
| UC-07 | 할일 수정      | P0       | 포함                 |

## 6. 비기능 요구사항

- **성능/동시접속**: 동시 접속 1,000명 기준으로 목록 조회·등록·수정·삭제 API가 정상 응답해야 한다 (구체 응답시간 목표는 2일 일정상 부하 테스트 생략, 향후 과제로 이연 — 10장 참조).
- **반응형 UI**: 웹 우선이며 모바일은 별도 네이티브 앱 없이 반응형 웹 UI(단일 코드베이스, 뷰포트 대응 레이아웃)로만 대응한다.
- **보안 최소 요건**: 비밀번호는 해시 저장(User.password, 도메인 정의서 3.1), 모든 API는 인증 필요(BR-01), 리소스 접근 시 소유권 검증(BR-02) 적용.
- **인증 방식**: JWT 기반. access_token(단명, API 요청 인증용)과 refresh_token(장명, access_token 재발급용)을 함께 사용한다. access_token 만료 시 refresh_token으로 재발급, refresh_token 자체가 만료/무효화되면 재로그인 필요.
- **접근성(a11y)**: 이번 범위에서 고려하지 않는다 (명시적 범위 제외).
- **가용성/확장성**: 별도 SLA 목표는 정의하지 않으며, 1,000명 동시접속 목표는 DB 커넥션 풀링 등 기본적인 확장 대비 수준으로 대응한다.

## 7. 기술 아키텍처 개요

| 계층       | 기술 스택                                                              |
| ---------- | ------------------------------------------------------------------------ |
| 프론트엔드 | React 19 + TypeScript, Zustand(전역 상태 관리), TanStack Query(서버 상태 동기화) |
| 백엔드     | Node.js + JavaScript + Express, pg 라이브러리로 PostgreSQL 직접 연동 (ORM 미사용, 순수 SQL/쿼리 빌더 방식) |
| 데이터베이스 | PostgreSQL 17                                                          |
| 배포/플랫폼 | 웹 우선, 모바일은 반응형 웹 UI로만 대응 (네이티브 앱 없음)              |

- ORM(Prisma 등) 사용 금지: 스키마·쿼리는 pg 라이브러리 기반 SQL로 직접 작성한다.
- 데이터 모델은 도메인 정의서 3장(User/Category/Todo)을 기준으로 테이블 설계한다.
- 인증: JWT access_token + refresh_token 방식. access_token은 API 요청 헤더로 전달, refresh_token은 재발급 전용으로 별도 보관(예: httpOnly 쿠키). 프론트엔드는 TanStack Query로 인증 API 연동, Zustand로 로그인 상태(access_token 등) 전역 관리.

## 8. 일정 및 마일스톤 (1인 개발, 2일)

**Day 1**: DB 스키마 설계(User/Category/Todo) 및 마이그레이션, 인증 API(UC-01/02, JWT access_token + refresh_token 발급/재발급), 할일 CRUD API(UC-04/05/07/08), 카테고리 기본값 처리(UC-09, BR-04) 구현.

**Day 2**: 필터링 API/화면(UC-06), 프론트엔드 화면(로그인/회원가입/할일 목록·등록·수정·삭제 UI) 구현 및 백엔드 연동, 반응형 레이아웃 적용, 통합 테스트 및 버그 수정. 시간 여유 시 UC-03(회원정보 수정) 추가.

## 9. 리스크 및 가정

- **일정 리스크**: 1인 개발 + 2일 일정으로 인해 UC-03(회원정보 수정) 및 상세 UX 다듬기가 후순위로 밀릴 수 있다.
- **동시접속 목표와 일정의 상충**: 1,000명 동시접속 검증(부하 테스트)은 2일 일정 내 수행하기 어려워, 코드 수준 기본기(인덱스, 커넥션 풀)만 반영하고 실측 검증은 향후 과제로 둔다.
- **ORM 미사용에 따른 개발 속도 리스크**: 순수 SQL 작성으로 인해 CRUD 개발 속도가 ORM 대비 느려질 수 있어 일정에 영향을 줄 수 있다.
- **도메인 미결 이슈 연관 리스크**: 아래 항목은 도메인 정의서 9장 미결 이슈와 직결되며, 확정 전까지는 임시 정책(수동 회피 또는 기능 보류)으로 대응한다.
  - OI-01(카테고리 삭제 정책) 미확정 → 2일 MVP에서는 카테고리 삭제 기능 자체를 구현하지 않아 리스크를 회피한다.
  - OI-02(카테고리명 변경 시 처리) 미확정 → 2일 MVP에서는 카테고리 rename 기능을 구현하지 않는다.
  - OI-03(회원 탈퇴 데이터 처리) 미확정 → 2일 MVP에서는 회원 탈퇴 기능을 구현하지 않는다.
