## 1. 문서 개요

**목적**: `2-PRD.md`(v0.2.0)에서 정한 MVP 범위(UC-01/02/04/05/06/07/08/09, P0/P1)를 실제 사용자가 앱을 이용하는 흐름으로 서술하여, 개발·QA 시 시나리오 기준으로 요구사항을 검증할 수 있게 한다.

**관련 문서와의 관계**: 용어, 엔티티, 비즈니스 규칙(BR-ID), 유스케이스(UC-ID), 수용 기준은 `1-domain-definition.md`(v0.4.0)를 단일 출처로 참조한다. 우선순위·범위·기술 스택은 `2-PRD.md`(v0.2.0)를 참조한다. 본 문서는 이 두 문서를 재정의하지 않고 UC-ID/BR-ID를 인용만 한다.

---

## 2. 시나리오 전제

- **타겟 사용자**: 학생 및 20대~50대 직장인(PRD 2장). 개인 일정을 웹에서 간단히 관리하려는 사용자.
- **인증 전제**: 모든 할일/카테고리 기능은 로그인된 사용자를 대상으로 한다(BR-01, 도메인 정의서 1장 전역 전제). 인증은 JWT access_token(단명) + refresh_token(장명) 방식이며, access_token은 API 요청 헤더로 전달한다(PRD 6·7장).
- **소유권 전제**: 모든 조회·수정·삭제는 본인 소유 리소스에 한한다(BR-02).
- **범위 전제**: MVP는 UC-01/02/04/05/06/07/08/09(P0/P1)이다. UC-03(회원정보 수정, P2)은 일정 여유 시에만 포함되므로 4장에서 짧게만 다룬다.

## 3. 핵심 사용자 시나리오

### 시나리오 1. 학생이 과제 마감을 관리한다

**관련 UC-ID**: UC-01, UC-02, UC-04, UC-05

**상황/맥락**: 대학생 지연씨는 여러 과목의 과제 마감일을 놓쳐 급하게 처리하는 일이 잦아, TodoList로 과제 일정을 관리하려 한다.

**단계별 흐름**:
1. 지연씨는 서비스에 처음 방문해 email/password/name으로 회원가입한다(UC-01).
2. 가입한 계정으로 로그인하여 access_token/refresh_token을 발급받는다(UC-02).
3. "알고리즘 과제" 할일을 제목, 시작일(오늘), 종료일(1주 후)로 등록한다. 카테고리는 지정하지 않는다(UC-04).
4. 이어서 "DB 프로젝트 발표자료" 할일을 다른 기간으로 등록한다(UC-04).
5. 목록 화면에서 자신이 등록한 할일 전체를 조회한다. 각 항목에는 계산된 상태(시작 전/진행중/완료/지연)가 함께 표시된다(UC-05).

**기대 결과**: 지연씨는 본인이 등록한 할일만 조회되고(BR-02), 카테고리를 지정하지 않은 할일은 자동으로 '기본' 카테고리로 분류된 것을 확인한다(BR-04).

---

### 시나리오 2. 직장인이 업무를 카테고리별로 관리하고 필터링한다

**관련 UC-ID**: UC-02, UC-04, UC-06, UC-09

**상황/맥락**: 직장인 민준씨는 "업무"와 "개인" 할일이 섞여 있어, 카테고리로 나눠 필요할 때만 골라 보고 싶다.

**단계별 흐름**:
1. 민준씨는 로그인한다(UC-02).
2. "분기 보고서 작성" 할일을 등록하며 카테고리를 "업무"로 지정한다(UC-04, UC-09).
3. "치과 예약" 할일을 등록하며 카테고리를 "개인"으로 지정한다(UC-04, UC-09).
4. 목록 화면에서 카테고리 "업무"로 필터를 적용해 조회한다(UC-06).
5. 이어서 상태 조건을 "진행중"으로 추가 필터링한다(UC-06).

**기대 결과**: 카테고리 및 상태 조건에 부합하는 할일만 반환되며(BR-02, BR-06 기반 계산 상태), 타 카테고리/타 상태의 할일은 결과에서 제외된다.

---

### 시나리오 3. 지연된 할일을 확인하고 완료 처리한다

**관련 UC-ID**: UC-02, UC-05, UC-06, UC-07

**상황/맥락**: 직장인 서연씨는 지난주 종료일이 지난 할일을 놓쳤는지 확인하고, 처리가 끝난 항목은 완료로 표시하려 한다.

**단계별 흐름**:
1. 서연씨는 로그인한다(UC-02).
2. 목록 조회 시 "거래처 미팅 자료 정리" 할일의 상태가 '지연'으로 표시된 것을 확인한다. 이 할일은 종료일이 지났고 isDone=false 상태다(UC-05, 도메인 정의서 5장 상태 판별 규칙).
3. 상태 필터를 "지연"으로 지정해 지연된 항목만 모아 확인한다(UC-06).
4. 이미 처리를 끝낸 "거래처 미팅 자료 정리"를 편집 화면에서 완료로 표시하고 저장한다(UC-07).

**기대 결과**: 완료 처리 시 completedAt이 기록되고(BR-07), 이후 목록에서는 종료일이 지났음에도 '지연'이 아닌 '완료'로 표시된다(도메인 정의서 5장, "완료된 할일은 종료일이 지났어도 지연이 아닌 완료로 표시").

---

### 시나리오 4. 잘못 등록한 할일을 수정·삭제한다

**관련 UC-ID**: UC-02, UC-07, UC-08

**상황/맥락**: 지연씨는 과제 제출 기한이 변경되어 종료일을 수정하고, 취소된 과제는 목록에서 삭제하려 한다.

**단계별 흐름**:
1. 지연씨는 로그인한다(UC-02).
2. "DB 프로젝트 발표자료" 할일의 편집 화면에서 종료일을 새 기한으로 변경하고 저장한다(UC-07).
3. 교수님이 취소한 "특강 과제" 할일을 목록에서 선택해 삭제한다(UC-08).

**기대 결과**: 종료일 변경 시 startDate <= endDate 조건을 만족하면 변경이 반영되고(BR-05), 삭제한 할일은 목록에서 즉시 제거된다. 두 작업 모두 본인 소유 할일에 대해서만 수행 가능하다(BR-02).

---

### (선택) 시나리오 5. 회원정보를 수정한다 — P2, 일정 여유 시

**관련 UC-ID**: UC-03

**상황/맥락**: 민준씨는 로그인 후 표시 이름과 비밀번호를 변경하고 싶다. PRD 5장 기준 UC-03은 P2로, MVP 필수 범위가 아니며 일정 여유 시에만 구현된다.

**단계별 흐름**: 로그인된 상태에서 본인 name/password 수정을 요청하면 정보가 반영된다(UC-03).

**기대 결과**: 타인의 회원정보 수정 시도는 거부된다(BR-02).

## 4. 예외/엣지 케이스 시나리오

### 4.1 access_token 만료 후 재발급

**관련 규칙**: PRD 6·7장(JWT 인증 방식), BR-01

**관련 UC-ID**: UC-05

- **상황**: 서연씨가 목록 조회 중 access_token이 만료된다.
- **흐름**: API가 인증 실패를 반환하면 클라이언트는 보관 중인 refresh_token으로 재발급을 요청한다. 재발급된 access_token으로 원래 요청을 재시도한다.
- **기대 결과**: 사용자는 재로그인 없이 작업을 이어간다. 단, refresh_token 자체가 만료/무효화된 경우에는 재발급이 거부되고 재로그인이 요구된다.

### 4.2 소유권 위반 시도

**관련 규칙**: BR-02

- **상황**: 민준씨가 타인의 할일 ID를 조작해 수정/삭제/조회를 시도한다(UC-07/UC-08 관련).
- **흐름**: 서버는 요청자(access_token의 사용자)와 리소스의 userId를 비교한다.
- **기대 결과**: 소유자가 일치하지 않으면 요청은 거부된다(BR-02).

### 4.3 날짜 유효성 위반

**관련 규칙**: BR-05

- **상황**: 지연씨가 할일 등록/수정 시 종료일을 시작일보다 이전으로 입력한다(UC-04, UC-07).
- **흐름**: 서버가 startDate <= endDate 조건을 검증한다.
- **기대 결과**: 조건을 만족하지 않으면 등록/수정이 거부되고 사용자에게 오류가 안내된다.

### 4.4 이메일 중복 가입 시도

**관련 규칙**: BR-03

- **상황**: 지연씨가 이미 가입된 email로 재가입을 시도한다(UC-01).
- **흐름**: 서버가 email 유일성을 검증한다.
- **기대 결과**: 중복 email이면 가입이 거부된다.

### 4.5 인증 없이 API 접근 시도

**관련 규칙**: BR-01
**관련 UC-ID**: UC-04~UC-09 (인증이 필요한 할일/카테고리 API 전반)

- **상황**: 로그인하지 않은 사용자가 할일/카테고리 API(UC-04~UC-09)를 직접 호출한다.
- **기대 결과**: 모든 요청이 거부되며 로그인이 요구된다.
